## Concrete source lifecycle defect

At exact57a, `tests/test_live_moomoo.py:328–353` creates a manual event loop on an owned daemon thread, starts `feed.run()`, cancels it at teardown, cancels the transport's poll task, and joins the pump thread. It never closes that loop or shuts down its default executor. Cancelling a task and joining the loop thread do not close executor-worker threads associated with the event loop.

Those workers are used directly: the synthetic Moomoo transport calls `asyncio.to_thread` for stock-quote and ticker reads (`src/quantmesh/live/moomoo.py:149,152`), and the feed's tick loop calls `asyncio.to_thread(self.prune_if_due, now)` (`feed.py:797`) after its one-second tick even when the feed has no persisted lake. Production feed cancellation gathers its supervisor/drain/tick tasks (`feed.py:772–779`), but event-loop/executor ownership belongs to the test runner that created the manual loop. The synthetic fixtures use canned `_StubOpenD`; they do not access the vendor daemon.

## Fork-safety boundary and follow-up scope

`_spawn_gated` calls `_native()` before pipe creation, signal-mask manipulation and `os.fork`. The child executes Python/ctypes/descriptor setup, so relaxing the single-thread requirement merely to accept a polluted pytest parent would change the launcher safety contract. The stricter live path additionally requires pinned Python3.12 isolated/no-site/no-bytecode execution and a single kernel task. A pytest3.13 process is not itself that production execution context; tests use the nonlive guard around synthetic owned children.

The observed local cause is the earlier test fixture's failure to finish its owned event-loop lifecycle.
